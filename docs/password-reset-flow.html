Password reset flow

HOTEL-BOOKING-APP  ·  REQUEST  →  RESET  →  CHANGE

WHAT THIS COVERS

Three endpoints, none of which exist yet. Phases 1 and 2 are the reset loop for someone locked out. Phase 3 is the separate, authenticated path for someone who is already signed in and just wants to change their password — today there is no way to do that at all, because update-user.dto.ts omits the password field.

PHASE 1 — REQUESTING A LINK

  1. The client posts an email address. The global ValidationPipe rejects anything that isn't a well-formed address with a 400 before the service is entered.
  2. findByEmail looks the account up. The password hash is select: false and is deliberately not requested — this phase never touches it.
  3. If the account exists: generate 32 random bytes as a hex string. That raw string is what goes in the email. What gets stored is only its SHA-256 digest, alongside an expiry 15 minutes out.
  4. If it doesn't: nothing is written and nothing is sent.
  5. Both branches return a byte-identical 200. That is the whole point of drawing them converging: if the "unknown address" case returned a 404, the endpoint would become a free tool for testing which of your guests have accounts.

Storing a digest rather than the token itself means a leaked database dump contains no usable reset links. SHA-256 is the right primitive here rather than bcrypt — the token already carries 256 bits of entropy so it cannot be brute-forced, and a fast unsalted digest is what allows the single indexed lookup in phase 2. A bcrypt hash would force a scan of every user in the collection.

PHASE 2 — SPENDING THE TOKEN

  1. The link in the email points at the frontend, not at this API. The frontend collects the new password and posts it back with the token. The token never appears in a URL this server logs.
  2. The submitted token is hashed and used to find a user whose stored digest matches and whose expiry is still in the future. Both conditions live in the query. Fetching the row and then checking the date in an if would work, but keeping it in the query means there is no code path that can forget to check.
  3. No match → 401. Wrong token, expired token, and already-used token are deliberately indistinguishable.
  4. A live token assigns the new plaintext password and clears the digest and expiry — in the same save. That single write is what makes the token single-use: once the digest is gone, the phase-2 lookup can never match it again, so a replay falls into the 401 branch.
  5. The save fires the existing pre('save') hook, which bcrypt-hashes the password. This is the load-bearing detail: findByIdAndUpdate — which UsersService.update() already uses — does not fire that hook. Writing a password through an update query would store it in plaintext and re-introduce the exact bug CHANGES.md documents fixing.
  6. Returns a message, not a session. Auto-signing-in on reset would make a stolen link strictly more valuable than it needs to be.

PHASE 3 — CHANGING IT WHILE SIGNED IN

Structurally simpler because there is no token to manage. The existing JwtAuthGuard establishes who is asking, the user is loaded with an explicit +password select, and bcrypt.compare checks that the caller knows the current password — without that check, a borrowed laptop with an open session is enough to lock the real owner out. A new password identical to the current one is a 400. The write is the same assign-then-save() mechanic as phase 2.

DELIBERATELY NOT IN SCOPE

Three gaps left open by decision, recorded here so they are not mistaken for oversights:

  • Existing sessions survive a reset. JWTs are stateless and live for 24 hours, so an attacker holding a token keeps access after the victim resets. Closing this needs a passwordChangedAt field checked in JwtStrategy. This is the one most worth revisiting.
  • No rate limiting. /auth/forgot-password can be used to mailbomb any address, and response timing still leaks a little about which addresses exist even though the body does not.
  • No resend-verification endpoint, so the comment in auth.service.ts promising one remains inaccurate.
