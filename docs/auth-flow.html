AUTH REFERENCE  /  HOTEL-BOOKING-APP

How authentication works now

Three flows — register, login, and reaching a protected route — plus the one secret that ties the last two together. Everything below is the verified, working path.

01 Registration

The password is hashed inside the Mongoose pre('save') hook, not in a service. That matters: save() is the one gate every write passes through, so a caller cannot forget to hash — there is no caller involved in the decision.

02 Login

The stored hash is marked select: false, so ordinary queries never return it and it cannot leak through a response by accident. Login is the one place allowed to ask for it, which is why it goes through findByEmailWithPassword() rather than the plain findByEmail().

03 Reaching a protected route

The token from step 1 or 2 goes back on every subsequent request as Authorization: Bearer <token>. JwtStrategy pulls it off the header, verifies the signature, and hands the decoded payload to your controller as req.user.

WIRED ON ONE ROUTE

GET /users/me carries @UseGuards(JwtAuthGuard) and is verified working — no token, a garbage token, and a token forged with the old hard-coded secret all return 401. Every other endpoint is still open, including BookingController, which has no routes at all yet.

04 The one secret, two consumers

Signing and verification must read the same key. They didn't — that was a real bug sitting in the code, and it is worth understanding because it fails in a way that gives you no useful error at all.

WHAT WAS BROKEN

The module signed with process.env.JWT_SECRET || 'yourSecretKey' and the strategy verified with configService.get('JWT_SECRET')!. Your .env defines AUTH_SECRET, so signing silently used the literal string 'yourSecretKey' while verification got undefined. Every valid token would have been rejected, with no error explaining why — the ! was asserting to the compiler that a genuinely missing value was present.

06 What changed to get here

FILECHANGE
user.schema.ts Added the pre('save') bcrypt hook and marked password as select: false. The hook takes no next callback on purpose — Mongoose detects an async hook and awaits the promise instead of passing one.
users.service.ts Dropped the bcrypt import that was never called. Added findByEmailWithPassword() for login.
auth.service.ts No longer hashes — the schema owns that. Two places hashing would double-hash and lock the user out permanently.
auth.controller.ts Real POST /auth/register and POST /auth/login routes. The class was an empty body.
auth.module.ts Registers AuthController and JwtStrategy, neither of which was wired in. Reads AUTH_SECRET via getOrThrow.
jwt.strategy.ts Same AUTH_SECRET via getOrThrow, replacing the ! assertion on a missing key.
main.ts Global ValidationPipe. Without it your class-validator decorators never ran, and a client could smuggle role: "admin" into a registration payload.
user.schema.spec.ts New — hook registered, plaintext becomes a hash, unmodified password is not re-hashed.

07 Still on your plate

MIGRATION

Users written before this fix are still stored in plaintext. The hook only fires on new saves — it will not reach back. Treat those passwords as compromised: hash them in place with a one-off script, or drop the collection if it is still dev data.

GUARDS

Only GET /users/me is protected. POST /users, GET /users, GET /users/:id, PATCH and DELETE are all still open — add @UseGuards(JwtAuthGuard) to the ones that need a signed-in user.

GOTCHA

findByIdAndUpdate is query middleware and does not run pre('save'). UpdateUserDto omits password today so there is no hole, but a future change-password feature must load the document and call .save(), never update in place.

OPEN ROUTE

POST /users still creates users. It hashes correctly now via the same hook, but it is unauthenticated and sits beside /auth/register doing nearly the same job. Consider guarding it as an admin-only endpoint.

PRE-EXISTING

Five test suites fail, untouched by this work: app.controller.spec expects "Hello World!" while AppService returns "Hello Haroon!", and four Nest scaffolding specs instantiate services with none of their dependencies provided.
